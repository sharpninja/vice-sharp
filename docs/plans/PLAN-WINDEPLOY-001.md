## 1. Current state (measured)

## 2. Decisions (locked by this plan unless Payton changes them)

1. Scope: the Windows desktop deployment contract, which is `PublishMsi`, `InstallMsi` and `PublishWinget`. The Xbox targets are excluded here and follow `PLAN-XBOXWASM-001` decision 9 (operator confirm item 1 below).
2. Shape: mirror the Linux precedent. The decision logic of the three targets moves into a new pure `internal` file `build/WindowsDeployment.cs` (namespace `ViceSharp.Build.Packaging`, beside `UserLocalDeployment.cs`); the `Executes` bodies keep only the process calls (`DotNetPublish`, `DotNetBuild`, `msiexec`, `wingetcreate`) and call the pure functions. Behavior and bytes of every produced artifact stay identical; this is an extraction, not a redesign.
3. Pure functions to extract (names fixed here so the tests can be written first): `MsiPublishPlan.Create(configuration, msiAllowDebug, msiAotEnabled, msiEnableDebugGrpc, token, port)` returning the publish property set, the prune globs and the validation outcome (throws with the existing messages); `MsiArtifactLocator.Locate(installerBinRoot, configuration)` returning the produced MSI path by the existing `en-US` then parent search and the rename decision; `MsiInstallPolicy.Compose(msiPath, logPath)` returning the `msiexec` argument string and `MsiInstallPolicy.IsSuccess(exitCode)` (0 and 3010) with the existing error text for 1925 and 1603; `ElevationSelector.Select(isElevated, pathProbe)` returning direct, `gsudo`, `sudo` or the existing actionable error; `WingetManifestSet.Create(packageId, version, msiSha256, msiUrl, locale fields)` returning the three manifest texts byte-identical to the current string literals; `WingetSubmitDecision.Create(exists, version, url, dryRun)` returning the `wingetcreate` command line; `WingetTokenSource.Select(wingetPat, githubToken)`.
4. Tests: `build.tests/Packaging/WindowsDeploymentTests.cs`. Pure cases (property sets, prune globs, argument strings, manifest bytes, exit-code policy, token and elevation selection) carry no host trait and run on both hosts. Cases that need Windows filesystem or process semantics (MSI location under a real `installer/bin/x64/<Configuration>` tree with the `en-US` subfolder, Administrator detection, `msiexec` and `WinAppDeployCmd` resolution) carry `[Trait("Host", "Windows")]`, and `BuildTest` adds `Host!=Windows` to its filter on non-Windows hosts, the mirror of the existing `Host!=Linux` rule; the excluded count is stated in the log on both hosts (ac-12 wording already covers "host-specific cases are excluded by host filter, never skipped").
5. Golden bytes: before extraction, the three winget manifests and the `msiexec` argument string produced by the current code for a fixed input are captured as fixtures by a receipt script on LEGION2 (the only host that can run `PublishMsi`); the extracted functions must reproduce those bytes exactly. No manifest content changes in this plan; moving the manifests to object-built YAML is a separate requirement change, listed in section 7.
6. Gates (D3): the mock gate green (every pure case with negative controls: wrong configuration gate, wrong prune set, wrong exit code accepted, wrong manifest byte, wrong elevation choice); then the extraction with `Compile` 0 warnings, `BuildTest` green on both hosts with the excluded counts stated, `git diff --check`; then one real `PublishMsi` on LEGION2 whose MSI hash, size and manifest bytes equal the pre-extraction receipt; self-assessment written; no hostile review until step 12.
7. Nothing in `ViceSharp.slnx` changes; `build.tests` stays outside it; artifacts stay gitignored.

## 3. Requirement changes (captured on PAYTON-LEGION2 through the requirements workflow after approval, then mirrored; single-writer rule)
