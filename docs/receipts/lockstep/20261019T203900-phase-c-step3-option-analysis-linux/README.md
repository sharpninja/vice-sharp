## What the watchpoint path (option A) actually does

- `vic20mem.c` lines 536 to 557, `mem_toggle_watchpoints(flag, context)`: when `flag` is nonzero it points `_mem_read_tab_ptr` and `_mem_write_tab_ptr` at `_mem_read_tab_watch` and `_mem_write_tab_watch`; when `flag > 1` it also points the dummy tables there, otherwise the dummy tables stay on the `_nowatch` tables. It does not touch `_mem_read_base_tab_ptr` or `mem_read_limit_tab_ptr`.
- The monitor sets the flag from `mon_breakpoint.c` lines 159 to 171 (`update_checkpoint_state`): `toggle_watchpoints_func(1 | (break_on_dummy_access << 1), ...)` when any load or store watchpoint exists, and sets `monitor_mask[mem] |= MI_WATCH`.
- The watch functions (`vic20mem.c` 260 to 284, `zero_read_watch`, `read_watch`, `store_watch`) call `monitor_watch_push_load_addr` or `monitor_watch_push_store_addr` and then the real `_nowatch` function. The push functions (`monitor.c` 2853 to 2881) record only the address into a per-memspace array capped at `MONITOR_MAX_CHECKPOINTS`, set an "occurred" flag, and record no data and no clock.
- The core drains those arrays once per instruction: `6510core.c` line 517 to 519, `if (monitor_mask[CALLER] & MI_WATCH) monitor_check_watchpoints(LAST_OPCODE_ADDR, reg_pc)`, inside the per-instruction epilogue.
- `mem_mmu_translate` (`vic20mem.c` 527 to 534) returns `*base` from `_mem_read_base_tab_ptr` and `*limit` from `mem_read_limit_tab_ptr`, which `mem_initialize_memory` fills with page limits (`(end_page << 8) + 0xfd`, line 320) for RAM and ROM pages and 0 only for I/O pages (line 328). `JUMP` (`maincpu.c` 83 to 89) refreshes `bank_base`, `bank_start`, `bank_limit` through it, and `maincpu_resync_limits` (`maincpu.c` 519 to 524) re-runs it after memory configuration changes.
- With `bank_limit` nonzero the fetch macros bypass the tables entirely: `FETCH_OPCODE` reads `bank_base + reg_pc` directly (`vic20cpu.c` 115 to 135 for xvic; `6510core.c` 2064 to 2080 for x64sc) and `FETCH_PARAM` and `FETCH_PARAM_DUMMY` (`6510core.c` 537 to 538) read `bank_base[addr]` when `addr < bank_limit`.

Conclusion A, observation from source: enabling watchpoints routes LOAD and STORE (and dummy accesses only when `break_on_dummy_access` is on) through recording functions, but those functions capture the address only, at instruction granularity, without data or clock, and opcode and operand fetches inside the cached bank never reach them because the watch toggle leaves the bank cache active. Option A by itself does not cover fast fetch, does not give data, and does not give the half-cycle; it fails the step 3 contract by construction, not by probe. It can serve at most as a cross-check of addresses.

## What runtime table interposition with the fast path withheld (option B) relies on

- The four table pointers are global, not static: `vic20mem.c` lines 99 to 102 (`read_func_ptr_t *_mem_read_tab_ptr; store_func_ptr_t *_mem_write_tab_ptr; read_func_ptr_t *_mem_read_tab_ptr_dummy; store_func_ptr_t *_mem_write_tab_ptr_dummy;`), which matches LEGION2's nm finding (type B data). An external wrapper linked into the same executable can read them after `mem_initialize_memory` and install its own 0x101-entry tables of recording trampolines that call the originals, capturing address, the returned or stored data byte, and the access kind (read, write, dummy read, dummy write by table) at the moment of the access, together with `maincpu_clk` for the cycle.
- `mem_mmu_translate` is a global function in `vic20mem.c` called from `maincpu.o` (`JUMP`, `maincpu_resync_limits`), so `ld --wrap=mem_mmu_translate` intercepts every call; a wrapper that forwards to `__real_mem_mmu_translate` and then returns `*limit = 0` makes every `FETCH_OPCODE` and `FETCH_PARAM` take the `LOAD` branch, which goes through the (interposed) tables. No VICE source changes.
- The non-fast branch of the xvic `FETCH_OPCODE` (`vic20cpu.c` 125 to 134) loads the opcode byte, then `CLK_INC`, then the first operand byte, then `CLK_INC`, then the second operand byte when `fetch_tab` says the opcode is three bytes, so each fetched byte is attributed to its own cycle and address. The x64sc non-fast branch (`6510core.c` 2081 onward) starts with `o = LOAD(reg_pc)` and the refresh and stretch bookkeeping; I did not read past line 2087, so how its operand bytes are loaded and clocked is not claimed here and must be read before the x64sc wrapper is designed.
- Equivalence proof needed, as LEGION2 said: withholding the fast path changes the code path VICE executes but not the emulated semantics by design (the fast path is a cache of the same bytes); the proof is a register, clock and stdout trace of the ROM-only workloads with and without the wrapped `mem_mmu_translate`, byte-identical, before any observation is trusted.
