## (d) New finding: identity comparisons against table entries

`c64memsc.c` 613 to 628 (`check_256k_ram_write`), 656, 695, 717 to 736 compare table entries by function identity (`mem_read_tab[i][j] == ram_read`, `mem_write_tab[i][j] == ram_store`, and so on) to decide which pages the 256K, plus256k and plus60k expansions take over. They run inside `mem_initialize_memory` after `c64meminit` (902) and `cartridge_init_config` (918). If trampolines were present in the tables at that moment, every comparison would fail and the expansions would silently misconfigure. Consequence for the plan: the wrapper must never patch from inside a wrapped setter during initialization; patching happens only from the per-cycle hook and from a wrapped `mem_initialize_memory` after `__real_mem_initialize_memory` returns. The matches in `c64mem.c`, `c64dtvmem.c` and `scpu64mem.c` belong to other machines; nothing of this kind exists under `src/vic20`.

## Classification summary for the plan

- Pointer reassignment: intra-object on both machines (xvic 523; x64sc `mem_update_tab_ptrs` from `mem_pla_config_changed`); not wrappable; handled by patching contents.
- Content rewrites: on both machines every rewrite happens inside `mem_initialize_memory`, which is global with cross-object callers only, so `--wrap=mem_initialize_memory` can re-patch every row after the real function returns; the per-cycle rescan of the rows the live pointers resolve to remains the fail-closed guarantee for any rewrite the wrap does not see.
- Fast path: xvic Kernal ROM only; x64sc RAM, chargen, BASIC and Kernal ROM; all side-effect-free host arrays. No blocker for B found in S0.
